# Assessment: qualify the existing finite-field table hint

**Recommendation:** one small, general mathematical qualification of the existing
hint is justified, if the coordinator approves. Prefer the coverage/inverse
invariant below to an AES implementation recipe. Treat at most one new AES run
as a development experiment, then stop prompt tuning this case and reassess.
No production edit or model/vendor/hardware action was made for this assessment.

## Why this is a precision correction

The current GOLDEN_MODEL prompt already recommends computing GF(2^8) log/antilog
tables in one 255-step loop as an efficient alternative to expensive inverse
construction. That advice presupposes a generator whose multiplicative order
is 255 in the field defined by the chosen modulus. It never states or asks the
model to verify that prerequisite.

AES03 used exactly the suggested table strategy but repeatedly multiplied by
the polynomial residue x. Under the contract's modulus 0x11b, this walk covers
only 51 nonzero bytes. The incomplete table then produces an incorrect inverse
for most bytes. The failure is a concrete gap in the precondition of advice the
harness already supplies, rather than grounds for another role, more retries,
a corrected AES reference or relaxed qualification.

This is still adaptation to an observed curriculum failure. It is legitimate
domain guidance, but any later result must be described as development on that
known task, not success on an untouched held-out benchmark. Mathematical validity
does not establish that a model will follow the hint or that runtime cost improves.

## Official definition and independently checked facts

[NIST FIPS 197-upd1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197-upd1.pdf),
Sections 4.2, 4.4 and 5.1.1, defines byte-field multiplication by polynomial
multiplication and reduction with x^8+x^4+x^3+x+1, defines nonzero inverses, and
constructs SubBytes from inversion and an affine map. It also gives inverse
exponentiation as b^254. These definitions do **not** state the generator orders
below or prescribe our log-table implementation; those are independently
calculated here. The direct PDF URL initially timed out; the identical official
PDF was successfully opened through its indexed query URL.

`work/nov8_gf_guidance_probe.py` implements trusted small polynomial convolution
and long division, distinct from the archived generated byte-shift recurrence.
It does not execute generated code. Its result JSON verifies:

| Field modulus | Candidate generator | First return to 1 | Distinct nonzero values |
|---|---|---:|---:|
| `0x11b` | `0x02` | 51 | 51 |
| `0x11b` | `0x03` | 255 | 255 |
| `0x11d` | `0x02` | 255 | 255 |

The last control matters: banning 0x02 universally or always choosing 0x03 would
be an unjustified rule. The correct prerequisite depends on the specified field.
The 0x11b/0x02 counterexample demonstrates why an irreducible modulus does not
make the residue x a primitive generator.

For 0x11b/0x03, all 255 nonzero inverse products equal 1. The resulting inverse map
matches an independent exhaustive product search for all 256 inputs, including
zero handled separately. Applying the stated affine map gives a bijection and
the public anchors 00→63,01→7c,53→ed. The 256-byte result hash is
`c2d8e5eed6cbebd8625fc18f81486a7733c04f9b0129ffbe974c68b90308b4f2`.
Both constructions share the explicitly defined field multiplication and affine
map; this is not a comparison with a separately imported 256-entry reference
table. Only the summary/hash is retained, not a replacement S-box table for
generation.

## Smallest proposed wording

Append this qualification immediately to the existing log/antilog suggestion:

> Log/antilog tables require a primitive generator for the specified field:
> verify that its powers visit all 255 nonzero elements before repeating.
> Irreducibility alone does not guarantee that x is a primitive generator. Verify each
> nonzero value multiplied by its computed inverse equals1 using field
> multiplication, and check the table anchors stated in the behavior.

Keep the current constant-table/one-time-init guidance, metering and sandbox.
This wording supplies an algorithm precondition and self-checks, not reference
code, a long table, an AES round answer, or a specific primitive element. The
verified0x02/0x03 facts belong in engineering evidence; they need not enter the
production prompt. If explicit numeric examples are added instead, disclose
them as domain knowledge and keep them conditional on the specified modulus.

For generalization, an alternative is to remove the existing specialized
log-table recommendation entirely. That is simpler text but discards useful
performance guidance without addressing its missing prerequisite. The small
qualification better repairs the advice already present. No further algorithm
menu, role or recovery flow is warranted by this one failure.

## Acceptance and finite experiment boundary

Before implementation: record this observed advice/precondition failure and
the selected wording. A prompt-delivery test must confirm the actual oracle
request contains the generator/coverage condition without replacing the
contract. Independent arithmetic controls must distinguish the failed 51-value
walk, a valid 255-value walk, and the different-modulus valid 0x02 control. Keep
ordinary module-local/controller and sandbox regressions. Do not add a runtime
requirement to inspect arbitrary user state for an AES-shaped S-box.

If approved and software validation passes, run **one** fresh AES04 with the
same published contract, independent checker, current qualified CLI/hash,
requested model and original limits. Preserve AES03 and all outcomes; do not
resume or regrade it. Record whether the round oracle qualifies, subsequent
module/whole-design verification, time, calls and tokens. Do not automatically
run AES05 or expand a budget when the attempt fails.

Stop after that declared experiment. Success establishes one execution on this
adapted curriculum task; failure calls for a feature/curriculum assessment, not
another narrowly tailored algorithm hint. The unobserved actual model identity,
adaptive task selection, prior CLI change and single trial prohibit a causal
or general model-superiority headline. Hidden public-benchmark tasks and their
graders remain outside these prompt-development trials.
