# AutoRTL expert review — November 15, 2026

Reviewer: Claude (coordinator since November 14), after reading the design,
harness, tests and evidence, running the first external benchmark pilots and
fixing what they exposed. Audience: the owner, and any agent continuing the
work. The action plan that follows from this review is `docs/ROADMAP.md`.

## Verdict

This is a strong portfolio project with one unusual asset and one unfinished
argument.

The asset is **evidence discipline on real hardware**. Twelve generated cores
ran on a Basys 3 against independent models, a generated UART echoed a million
bytes without error, every claim is bound to hashed artifacts that CI audits,
and testbenches must fail injected faults before they may grade anything. Very
few student or hobby FPGA projects can show that chain.

The unfinished argument is **"the harness is the contribution."** Until
November 14 nothing compared the harness with a simpler workflow. The first
comparison (six pilot tasks) shows a single model call passing 6/6 at about
1/15 of the tokens, the harness passing 6/6 only after four harness defects were
fixed, and one case where the harness verified and accepted a wrong design. On
easy functional tasks the harness does not earn its cost. Its real edge is
elsewhere: measured area and timing optimisation, multi-module builds, and
hardware-proven results. The project should say that, and prove it.

A hiring manager or reviewer will ask three questions. Current answers:

| Question | Answer today | Gap |
|---|---|---|
| Does it work on real hardware? | Yes, well evidenced | A two-minute demo recording |
| Is it better than just asking a model? | Not shown; pilot says "not on easy tasks" | Final 360-run result; a benchmark where optimisation matters |
| Can I trust and run it? | Tests and audit are excellent; repo is hard to enter | Licence, pushed branch, 150-line README, one agent guide |

## What is genuinely good

1. **Verification before trust.** Static checks, compile, simulation against a
   generated testbench that was itself mutation-qualified, then routed metrics
   with an integrity gate. Selection is deterministic and timing-first.
2. **Failure taxonomy as a habit.** Every defect becomes a named entry before
   its fix. In one day of external tasks this captured ten new entries with
   causes and repairs; that is how the harness actually improves.
3. **Honest accounting.** Infrastructure failures never count as design
   verdicts; budgets are charged for every call; aborted attempts are kept.
4. **Tests.** About 2,300 harness tests and 320 tooling tests, including
   byte-identical template goldens and real-log fixtures.
5. **Backend independence.** Roles run on Codex CLI, any OpenAI-compatible API
   or a local command.

## Findings, most important first

### F1. The public repository does not show the project (critical, cheap)

- No `LICENSE`. Legally nobody may reuse the code, and reviewers notice.
- `main` is frozen at `ca61dbc`; the working branch has 20+ local commits that
  were never pushed. The benchmark, the catalog, the pilot evidence and four
  harness fixes exist only on one laptop.
- README is 507 lines and leads with a dense list. It has no benchmark result
  and no single picture of the loop running.

### F2. The central claim is untested where it matters (critical)

- The registered comparison (40 tasks x 3 arms x 3 trials) is running; it must
  be graded, reported with intervals and published whatever it shows.
- Half the registered set is trivial combinational logic (the proportional rule
  did that). Expect near-ceiling results for every arm; ceiling results cannot
  show a harness advantage.
- The comparison is functional only. The harness's distinctive capability is
  optimisation (AES 9,108 to 614 LUTs, FIR closing 150 MHz). No experiment
  compares optimised area/timing against a single call on correct designs.
- The model is recorded as `unobserved-cli-default`. A controlled claim needs a
  pinned model name.
- The single-call arm is one invocation, not a tools-enabled coding agent. Any
  "better than an agent" claim needs that separate baseline.

### F3. Self-consistent verification can accept wrong designs (high)

In pilot-04 the planner misread a state table; the generated oracle and the RTL
both implemented the wrong spec, and the harness accepted a design that fails
the official test (`planner_spec_error_shared_by_oracle_and_rtl`). Internal
verification only checks RTL against the planner's interpretation. This is the
most interesting research question in the repository and currently has no
mitigation or measurement beyond one occurrence.

### F4. The curriculum had overfit to its own designs (high, now partly fixed)

The first six external tasks exposed defects that 2,000 tests and seven
curriculum tiers had not: purely combinational designs were never timed,
single-register designs were never timed out of context, modules without a
reset could not be specified, an unstartable tool was "unknown", and a Vivado
crash was a "design" failure. All are fixed with tests and live checks. The
lesson is structural: the curriculum needs a standing tier of external tasks.

### F5. Process weight exceeds product weight (medium)

- Six overlapping entry documents (START_HERE, AGENTS, CLAUDE, GEMINI,
  AGENT_HANDOFF, SESSION_HANDOFF), about 7,500 lines of docs in total.
  SESSION_HANDOFF now stacks "Earlier" sections; DESIGN.md carries dated
  change notes; TASKS.md is 1,300 lines.
- The coordinator lease expires after about an hour and lapsed five times in
  one day (machine sleep, long tool runs). Each lapse costs a reclaim of every
  file scope. The protocol is sound; its ergonomics are not.
- 122,928 evidence files are tracked. The pack is only 36 MiB, but a Windows
  checkout or `git worktree add` takes minutes.

### F6. Code health (medium)

- `autortl/fsm.py` is 1,700+ lines; `_run_optimize` is about 490 lines in one
  method. It is the place every new feature touches.
- Private names are used across modules (`doctor._resolve`,
  `artifacts._manifest`).
- No linter or type checker in CI; `requirements.txt` is unpinned; no
  `pyproject.toml`; CI runs Python 3.12 while development ran 3.14.
- The benchmark was driven by a shell script and a grading script outside the
  repository (fixed on November 15: `benchmark/campaign.py`,
  `benchmark/report.py`).

### F7. Operations (medium)

Host sleep stalled runs twice and agents once. The harness recovered correctly
each time, which is a credit to its design, but an 18-hour campaign needs an
awake machine and a supervisor that survives restarts.

## Recommendations

1. **Publish first.** Licence, push, short README, tagged release. An excellent
   private repository is worth nothing on a CV.
2. **Report the registered comparison exactly as it lands**, including false
   acceptances and cost. A careful negative or mixed result is more credible
   than a headline.
3. **Reframe the contribution** as *verified, measured, hardware-proven RTL
   from bounded model roles*, with three pillars: hardware proof, verifier
   qualification, measured comparison. Do not claim the harness beats a single
   call on functional pass rate unless the data says so.
4. **Add the benchmark the harness should win:** area/timing on correct designs
   for harder tasks, with a pinned model, plus a small external-task tier in
   the curriculum.
5. **Attack false acceptance** with one measured mitigation (independent
   derivation of examples from the original request), using the pilot
   machinery as the instrument.
6. **Cut process to what recovery needs:** one agent guide, one current
   checkpoint, dated history only in PROGRESS and Git.
7. **Then refactor** `fsm.py` under the existing tests.
